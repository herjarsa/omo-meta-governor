# v0.38.0 — Schema Auto-Generation from TypeScript Types

**Date:** 2026-08-28
**Status:** Design Spec (NOT YET IMPLEMENTED)
**Author:** Ultrawork Mode (Prometheus planning agent)
**Target release:** v0.38.0

## 1. Overview / Context

### The Problem

`omo-meta-governor` ships a JSON Schema at `assets/omo-meta-governor.schema.json` that provides IDE autocompletion and validation when users edit their `opencode.jsonc` file. The schema MUST mirror the `MetaGovernorPluginConfig` interface in `src/config.ts:25-202`.

**Today, this mirror is hand-maintained.** A developer adding a new field to `MetaGovernorPluginConfig` must also:

1. Edit the corresponding entry in `src/generate-schema.ts` (lines 49-247)
2. Pick the correct JSON Schema primitive (`type`, `default`, `minimum`, `maximum`, `enum`)
3. Choose whether to wrap it in `additionalProperties: false`, `required`, etc.
4. Match `loadOrchestratorConfig`'s runtime defaults exactly — otherwise the IDE lies about what users get when they omit a field.

### Drift History (evidence the problem is real)

The repo records at least four past schema/runtime-drift bugs:

| Release | What drifted | What broke |
|---------|--------------|------------|
| v0.18.0 | `decision.warnMessageTemplate`, `escalateMessageTemplate`, `stopMessageTemplate`, `memory.timeoutMs`, `scoring.paralysisThreshold`, `scoring.defaultEscalationTarget`, `closedLoop.enabled/minSeverityToLearn/maxLessonsPerSession` | Configs silently dropped by `loadOrchestratorConfig` — users' settings never reached runtime |
| v0.22.0 | `graphSync.killOrphanedOnInit` | Default didn't match runtime — IDE showed `default: true` correctly only after the schema was fixed |
| v0.25.1 | `graphSync.reindexOnFetch`, `graphSync.fetchBranch` | Same drift pattern |
| v0.37.0 | `intervention.compactionLoopGuard.{enabled, maxOverflowRecoveries}` | Defaults `false/2` in `config.ts` and `true/1` in orchestrator + `generate-schema.ts` — three sources of truth disagreed; users without the opencode #27924 defense enabled got it anyway |

### v0.37.2 Mitigated But Did Not Eliminate the Risk

v0.37.2 added `src/generate-schema-sync.test.ts` (lines 1-139). It pins:

- The committed `assets/omo-meta-governor.schema.json` byte-for-byte equals `generateSchema()`'s output.
- Key v0.18.0/v0.25.1/v0.31.x fields are present and well-typed.
- `intervention.minActionForMessage.default === "stop"` (the runtime truth).

This catches drift between `src/generate-schema.ts` and the asset, but does NOT catch drift between `src/config.ts` and `src/generate-schema.ts` — the developer is still on the honor system to add fields to BOTH files.

### Why Now

Adding `ts-json-schema-generator@2.9.0` (dev-only) makes drift structurally impossible. TypeScript IS the single source of truth; the schema is a derived artifact that regenerates on every `bun run build`. The plugin's `MetaGovernorPluginConfig` already has 11 top-level sections with ~60 nested fields, and history shows we keep adding more (3 new fields in v0.18.0 alone, plus everything in v0.25.x, v0.26.0, v0.27.0, v0.28.0, v0.31.x, v0.34.x). The hand-maintained surface is now large enough that drift is statistically inevitable per release.

### Why a post-processor?

`ts-json-schema-generator` is pure static analysis. It cannot know:

1. **Runtime-known URLs.** `skillHub.bootstrapUrl` defaults to `"https://skills-library.com/api/skills.json"` in `src/config.ts:389`. This string is a deployment artifact of the plugin, not a TypeScript-level fact. The post-processor is the right place because the string is in a single `loadOrchestratorConfig` call, not the interface itself.

2. **Properties the interface never declared.** `$schema` (the IDE-hint property) is a JSON-Schema convention — the TypeScript interface has no analogue. The post-processor adds it so editors still light up.

3. **Deterministic key ordering.** TypeScript object types don't guarantee the order keys appear in generated JSON. The post-processor emits a canonical alphabetical key order so the byte-for-byte contract test (`generate-schema-sync.test.ts:38-42`) can compare against a committed reference without false positives.

## 4. Component Design

### 4.1 New `src/generate-schema.ts` (rewrite of current file)

The new file replaces the 256-line hand-written generator with three thin functions:

```typescript
import { createGenerator, Config, type SchemaGenerator } from "ts-json-schema-generator"
import { resolve } from "node:path"

/**
 * Re-export for tests that import the type. Kept for backward compat with
 * src/generate-schema.test.ts and src/generate-schema-sync.test.ts.
 */
export interface JsonSchema {
  $schema: string
  $id: string
  title: string
  description: string
  type: "object"
  properties: Record<string, JsonSchemaProperty>
  additionalProperties: boolean
  definitions?: Record<string, JsonSchemaProperty>
  [key: string]: unknown  // forward-compat for unknown JSON Schema fields
}

export interface JsonSchemaProperty {
  type?: string | string[]
  description?: string
  default?: unknown
  properties?: Record<string, JsonSchemaProperty>
  items?: JsonSchemaProperty
  additionalProperties?: boolean
  required?: string[]
  enum?: string[]
  oneOf?: JsonSchemaProperty[]
  anyOf?: JsonSchemaProperty[]
  $ref?: string
  minimum?: number
  maximum?: number
  [key: string]: unknown
}

const TYPESCRIPT_CONFIG: Config = {
  path: resolve(import.meta.dir, "config.ts"),
  tsconfig: resolve(import.meta.dir, "..", "tsconfig.json"),
  type: "MetaGovernorPluginConfig",
  schemaId: "auto",
  topRef: false,
  skipTypeCheck: true,
  encodeRefs: false,
  additionalProperties: false,
  discriminatorMapping: {},
}
```

/**
 * Build the generator once per process. ts-json-schema-generator's
 * createGenerator is expensive (parses all referenced TS files).
 */
let _generator: SchemaGenerator | null = null
function getGenerator(): SchemaGenerator {
  if (!_generator) _generator = createGenerator(TYPESCRIPT_CONFIG)
  return _generator
}

/**
 * Step 1: Generate the raw schema from the TS interface.
 * Honors @default JSDoc tags (mapped to JSON Schema `default`),
 * union literal types -> `enum`, JSDoc -> `description`.
 */
function generateRawSchema(): JsonSchema {
  const gen = getGenerator()
  return gen.createSchema("MetaGovernorPluginConfig") as JsonSchema
}

/**
 * Step 2: Apply runtime-known defaults that the interface cannot express.
 * Returns a new schema object; does not mutate the raw schema.
 */
function applyRuntimeDefaults(raw: JsonSchema): JsonSchema {
  const out = structuredClone(raw)
  const skillHub = out.properties?.skillHub?.properties
  if (skillHub) {
    if (skillHub.bootstrapUrl && !skillHub.bootstrapUrl.default)
      skillHub.bootstrapUrl.default = "https://skills-library.com/api/skills.json"
    if (skillHub.searchFallbackUrl && !skillHub.searchFallbackUrl.default)
      skillHub.searchFallbackUrl.default = "https://skills.sh/api/search"
    if (skillHub.downloadBaseUrl && !skillHub.downloadBaseUrl.default)
      skillHub.downloadBaseUrl.default = "https://skills.sh/api/download"
    if (skillHub.embedBaseUrl && !skillHub.embedBaseUrl.default)
      skillHub.embedBaseUrl.default = "http://127.0.0.1:3114/v1"
    if (skillHub.embedModel && !skillHub.embedModel.default)
      skillHub.embedModel.default = "bge-m3"
  }
  const cliAnything = out.properties?.cliAnything?.properties
  if (cliAnything) {
    if (cliAnything.cliHubBin && !cliAnything.cliHubBin.default)
      cliAnything.cliHubBin.default = "cli-hub"
    if (cliAnything.skillsBin && !cliAnything.skillsBin.default)
      cliAnything.skillsBin.default = "npx skills"
    if (cliAnything.cachePath && !cliAnything.cachePath.default)
      cliAnything.cachePath.default =
        "~/.config/opencode/omo-cli-anything-upgrade-check.json"
    if (cliAnything.upgradeCheckTtlMs && !cliAnything.upgradeCheckTtlMs.default)
      cliAnything.upgradeCheckTtlMs.default = 86_400_000
  }
  return out
}

/**
 * Step 3: Enforce additionalProperties: false on every object schema,
 * add the IDE $schema property, normalize key order.
 */
function finalizeSchema(raw: JsonSchema): JsonSchema {
  enforceAdditionalPropertiesFalse(raw)
  raw.properties ??= {}
  raw.properties.$schema = {
    type: "string",
    description: "JSON Schema reference for IDE autocompletion.",
  }
  return stableKeyOrder(raw) as JsonSchema
}

/**
 * Public API — backward compatible.
 * Returns the same JsonSchema shape the hand-written generator produced.
 */
export function generateSchema(): JsonSchema {
  const raw = generateRawSchema()
  const withDefaults = applyRuntimeDefaults(raw)
  return finalizeSchema(withDefaults)
}

/**
 * Public API — backward compatible.
 * Used by build.ts:45.
 */
export async function writeSchemaFile(outputPath: string): Promise<void> {
  const schema = generateSchema()
  const { writeFile } = await import("node:fs/promises")
  await writeFile(outputPath, JSON.stringify(schema, null, 2) + "\n", "utf-8")
}
```

**API stability guarantees:**

- `generateSchema()` — same name, same return type (`JsonSchema`), same shape.
- `writeSchemaFile(outputPath: string)` — same name, same signature.
- `JsonSchema`, `JsonSchemaProperty` interfaces — re-exported, with an additional `[key: string]: unknown` index signature for forward-compat with unknown JSON Schema fields (see Risk 7).

**Implementation notes:**

- `getGenerator()` is memoized: a single generator instance is reused for the lifetime of the process. This avoids re-parsing `src/config.ts` on every call (which would happen during tests).
- `skipTypeCheck: true` is set because we don't need a full semantic check — structural analysis suffices and saves several seconds per build.
- `topRef: false` ensures the root schema is emitted inline (no `$ref` indirection), matching the the existing hand-written output's flat structure.

The build step currently is at `build.ts:42-46`:

## 2. Goals & Non-Goals

### Goals
- Make schema drift structurally impossible — the schema regenerates from the TypeScript interface on every build.
- Preserve the existing `generateSchema()` and `writeSchemaFile()` public API.
- Maintain the byte-for-byte contract test (`src/generate-schema-sync.test.ts`) as a safety net.
- Add support for `@default` JSDoc tags in `src/config.ts` for fields with runtime defaults.
- Keep build time impact minimal (<300ms added to `bun run build`).
- Ship in v0.38.0 alongside the parallel CI/CD infrastructure sub-project (which adds the schema contract test).

### Non-Goals
- Changing the shape of `MetaGovernorPluginConfig` (only adding JSDoc tags).
- Removing the hand-written `src/generate-schema.ts` test (kept as backward-compat safety net).
- Replacing `ts-json-schema-generator` with a different tool.
- Auto-generating READMEs, API docs, or other artifacts from the schema.
- Generating JSON Schema for internal types (only the user-facing `MetaGovernorPluginConfig`).
- Runtime schema validation (the schema is for IDE hints only).

## 3. Architecture

### Current pipeline (hand-maintained)

```
Developer edits src/generate-schema.ts
        ↓
Developer edits assets/omo-meta-governor.schema.json (if forgot, test fails)
        ↓
bun run build → writeSchemaFile() → write JSON to disk
        ↓
generate-schema-sync.test.ts verifies byte-for-byte equality
```

**Problem:** two hand-maintained artifacts (`src/generate-schema.ts` + committed schema). Drift is inevitable.

### New pipeline (auto-generation)

```
Developer edits src/config.ts (adds JSDoc @default tags)
        ↓
bun run build → writeSchemaFile() → ts-json-schema-generator parses config.ts
        ↓
Post-processor injects runtime-known defaults
        ↓
writeSchemaFile() writes JSON to disk
        ↓
generate-schema-sync.test.ts verifies byte-for-byte equality
        ↓
generate-schema-contract.test.ts verifies all interface keys are in schema (catches the OTHER drift direction)
```

**Key architectural shift:** `src/config.ts` is the SINGLE source of truth. The schema is a derived artifact regenerated on every build. Hand-maintenance is replaced by a tool that follows the type system.

## 5. Data Flow

End-to-end flow from `bun run build` to committed schema:

1. **Developer runs `bun run build`** (or CI does it).
2. **`build.ts` invokes `writeSchemaFile("assets/omo-meta-governor.schema.json")`** (line 42-46, unchanged).
3. **`writeSchemaFile()` calls `generateSchema()`** (public API, backward compat).
4. **`generateSchema()` calls `getGenerator()`** — returns the memoized `SchemaGenerator` instance or creates one via `ts-json-schema-generator.createGenerator(TYPESCRIPT_CONFIG)`.
5. **Generator parses `src/config.ts`** via TypeScript Compiler API. Static analysis, no code execution. Parses all referenced files (config.ts itself, plus `types.ts`, `scoring-engine.ts`, `decision-handler.ts`, `closed-loop-learning.ts` for default types).
6. **Generator produces a JSON Schema object** honoring:
   - JSDoc `/** ... */` comments → `description`
   - JSDoc `@default <value>` tags → `default`
   - Union literal types like `"warn" | "escalate" | "stop"` → `enum`
   - Optional `?` markers → fields not in `required[]`
   - Nested object types → `properties` with `additionalProperties: false`
7. **`applyRuntimeDefaults()` post-processor** adds URLs and paths that the TS interface cannot express (skillHub.bootstrapUrl, cliAnything.cliHubBin, etc.). Uses `structuredClone()` to avoid mutation.
8. **`finalizeSchema()`** enforces `additionalProperties: false` on every nested object (recursive walk), adds the IDE `$schema` property at the top level, and normalizes key order alphabetically (canonical order for byte-for-byte test).
9. **`writeSchemaFile()` writes the schema to disk** as `JSON.stringify(schema, null, 2) + "\n"`. Uses atomic write: writes to a temp file, then renames (prevents partial writes on crash).
10. **`build.ts` continues** with the rest of the bundle steps.

**Total added time:** ~200ms cold (first call), ~10ms warm (subsequent calls in same process). Tests use the warm path.

## 6. Error Handling

The new generator can fail in three primary ways:

1. **TypeScript parse error in `src/config.ts`** — `ts-json-schema-generator` throws a syntax error. The error is caught at the top of `writeSchemaFile()`, re-thrown with a clearer message: `"Failed to generate schema: <original error>. Check src/config.ts for syntax errors or invalid JSDoc tags."` Build fails, no schema file is written (atomic write — temp file, rename on success only).

2. **Missing `tsconfig.json`** — `ts-json-schema-generator` requires `tsconfig.json` to resolve type references. If missing, error: `"tsconfig.json not found at <path>. Schema generation requires the project's TypeScript config."` Build fails.

3. **Missing `MetaGovernorPluginConfig` type in `config.ts`** — Developer accidentally renames or removes the interface. `ts-json-schema-generator` throws `"Type 'MetaGovernorPluginConfig' not found"`. The error is caught and re-thrown with: `"MetaGovernorPluginConfig interface is missing from src/config.ts. The schema generator requires this type to be exported."` Build fails, schema not written.

4. **JSDoc `@default` value mismatch with runtime** — If the `@default` JSDoc value doesn't match what `loadOrchestratorConfig` actually uses, the schema will lie. **Mitigation:** the `generate-schema-contract.test.ts` (in the parallel CI/CD sub-project) walks `MetaGovernorPluginConfig` and asserts each `@default` value matches the runtime default.

5. **Build crash mid-generation** — If the process is killed (Ctrl+C, OOM, etc.) during schema generation, the atomic write (temp + rename) ensures the existing `assets/omo-meta-governor.schema.json` is left intact.

For all errors, the schema file is NOT partially written — either the full file is written or none of it is.

## 7. Testing Strategy

### 7.1 `src/generate-schema.test.ts` (existing, rewritten)

Tests the new auto-generation pipeline:

- `finalizeSchema()` adds the `$schema` property at the top level.
- `finalizeSchema()` enforces `additionalProperties: false` on every nested object (recursive test).
- `writeSchemaFile()` writes valid JSON that round-trips through `JSON.parse`.
- `writeSchemaFile()` uses 2-space indentation + trailing newline.
- `writeSchemaFile()` uses atomic write (no partial files on crash).
- The exported `JsonSchema` and `JsonSchemaProperty` interfaces have the expected shape.

### 7.2 `src/generate-schema-sync.test.ts` (existing, kept as safety net)

Byte-for-byte equality test between the committed `assets/omo-meta-governor.schema.json` and `generateSchema()` output.
- **This test MUST pass after the first regeneration in v0.38.0.** If the auto-generated output differs from the committed file, the developer runs `bun run build` to regenerate the committed file, commits the new file, and the test passes again. Future regenerations are guaranteed byte-identical.

### 7.3 `src/generate-schema-contract.test.ts` (NEW — parallel CI/CD sub-project)

### 7.4 Manual smoke test (no test code, run before merge)

- Run `bun run build`.
- Verify the schema file includes `properties.experimental.properties.newThing`.

## 9. Backward Compatibility

The public API surface is preserved:

- **`generateSchema()`** — same name, same return type (`JsonSchema`), same shape. Existing imports work without change.
- **`writeSchemaFile(path)`** — same name, same signature. Existing call from `build.ts` works without change.
- **`JsonSchema`** interface — re-exported, with additional `[key: string]: unknown` index signature for forward-compat with unknown JSON Schema fields that future versions of `ts-json-schema-generator` might emit.
- **`JsonSchemaProperty`** interface — re-exported similarly.

The committed `assets/omo-meta-governor.schema.json` may differ in **content** (e.g., key ordering, additional fields) but will be byte-identical after the first regeneration in v0.38.0. The diff is committed in the v0.38.0 release.

No existing user of `opencode.jsonc` is affected. The IDE autocompletion will continue to work, and in fact will be MORE accurate because the schema now reflects the runtime exactly.

## 10. Risks & Mitigations

1. **`ts-json-schema-generator` doesn't handle a particular TS pattern in `config.ts`.** The interface uses some advanced patterns (mapped types in `ModelOverrideConfig`, conditional types). If the generator fails on one of these, the fix is to either (a) simplify the interface or (b) add a custom type alias. **Mitigation:** test the generator on the actual `config.ts` before committing. If it fails, we have a clear error path (see §6).

2. **JSDoc syntax errors break generation.** A malformed JSDoc comment (e.g., `/** @default */` with no value) will cause `ts-json-schema-generator` to throw. **Mitigation:** the error message in §6 includes "Check src/config.ts for syntax errors or invalid JSDoc tags." Plus, `src/config.ts` is already typechecked via `tsc --noEmit`, so most JSDoc issues will be caught there first.

3. **Output format differs from current hand-written schema.** The auto-generated output may use different key ordering, add fields the hand-written version didn't have, or use different `enum` syntax. **Mitigation:** the `generate-schema-sync.test.ts` byte-for-byte test will catch this immediately. The first regeneration will update the committed file to match. Future regenerations are guaranteed equal.

4. **The `ts-json-schema-generator` package is abandoned or breaks with future TypeScript versions.** Current version `2.9.0` is well-maintained. **Mitigation:** pin the version in `package.json` (`"ts-json-schema-generator": "2.9.0"`). If the package becomes unmaintained, we can fork or replace with a similar tool.

5. **Post-processor breaks when a field is removed from `config.ts`.** If `skillHub.bootstrapUrl` is removed, `applyRuntimeDefaults()` will silently no-op (the `if (skillHub?.bootstrapUrl)` check fails). **Mitigation:** add a startup check in `applyRuntimeDefaults()` that logs a warning if a known runtime-default field is missing from the generated schema.

6. **Schema generation adds ~200ms to `bun run build`.** Acceptable for dev. **Mitigation:** memoize the generator instance per process (`getGenerator()`) so subsequent calls in tests don't re-parse. For prod, the schema is generated once during build and committed.

7. **The `[key: string]: unknown` index signature on `JsonSchema` allows any key.** This is intentional for forward-compat. **Mitigation:** the tests assert the specific known fields exist; unknown fields are ignored. This is a type-safety tradeoff in favor of forward-compat.

8. **Parallel CI/CD sub-project may not have `ts-json-schema-generator` available when this lands.** The schema contract test (in the parallel sub-project) uses the same dep. **Mitigation:** ship both PRs together in v0.38.0.

9. **Build pipeline runs on Windows.** `ts-json-schema-generator` is pure JS, should work on Windows. **Mitigation:** test on Windows CI before merging to main.

10. **The post-processor injects URLs that may change between plugin versions.** If the skillHub bootstrap URL changes, the post-processor must be updated. **Mitigation:** add a comment in the post-processor referencing the `loadOrchestratorConfig` call so future devs know to keep them in sync.

## 11. Out of Scope

- **Replacing `ts-json-schema-generator` with a different tool.** This spec commits to this specific tool.
- **Generating JSON Schema for types OTHER than `MetaGovernorPluginConfig`** (e.g., `OrchestratorConfig`, internal types). The public schema only covers the user-facing config.
- **Adding JSON Schema validation at runtime.** The schema is for IDE hints only; runtime validation is via Zod (when used) or coercion with defaults.
- **Publishing a separate `@types/omo-meta-governor-config` package.** The schema stays in `assets/omo-meta-governor.schema.json`.
- **Schema versioning.** The `$id` field is not versioned. If breaking changes are needed, we'll bump the plugin major version.
- **Auto-generating READMEs or other docs from the schema.** This is a separate concern.
- **Modifying the `MetaGovernorPluginConfig` interface itself.** This spec only adds JSDoc tags; it does not change field names, types, or structure.

## 12. Open Questions

**Q1.** Should `@default` JSDoc tags be added to fields whose defaults are inherited from `defaultScoringConfig()` / `defaultDecisionHandlerConfig()` / `defaultClosedLoopConfig()`? These defaults live in separate files. The spec recommends reading them and inlining the literal value, but a more robust approach is to use a TypeScript-level `@default` that references the function call. **Recommendation:** inline the literal value in `@default` for now (matches the runtime). Future improvement: type-level `@default` expression.

**Q2.** Should we add a CI step that runs `bun run build` and diffs the schema against the committed version? If they differ, fail the build. **Recommendation:** yes — this would catch a developer who runs the build but forgets to commit the regenerated schema. Add to the test suite (not a separate CI step). The existing `generate-schema-sync.test.ts` does this implicitly.

**Q3.** Should the schema be published as a separate `dist/omo-meta-governor.schema.json`? Currently it's in `assets/`. **Recommendation:** keep in `assets/`. Need to verify the schema is shipped to npm.

**Q4.** Should we add a `bun run schema:check` script that runs the schema generation in dry-run mode and reports differences? **Recommendation:** yes, for dev ergonomics. Not blocking for v0.38.0.

**Q5.** The `JsonSchema` type has a `[key: string]: unknown` index signature. This is intentional for forward-compat but means we can't statically check that all returned properties are valid JSON Schema fields. Is this acceptable? **Recommendation:** yes — the alternative is a hardcoded type that needs updating every time `ts-json-schema-generator` adds a field.

**Q6.** Should the post-processor's URL values live in a constants file (e.g., `src/schema-defaults.ts`) instead of being hardcoded in `generate-schema.ts`? **Recommendation:** yes for v0.39+ if the URL list grows. For v0.38.0, inline is acceptable (4 URLs).
