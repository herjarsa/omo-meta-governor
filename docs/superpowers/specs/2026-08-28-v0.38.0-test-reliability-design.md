# v0.38.0 — Test Reliability Design Spec

**Date:** 2026-08-28
**Status:** Design Spec (NOT YET IMPLEMENTED)
**Author:** Ultrawork Mode (Prometheus planning agent)
**Target release:** v0.38.0

---

## 1. Overview / Context

`omo-meta-governor` ships with a test suite of 1025+ passing tests across 88 files. However, **12 tests are skipped** on Windows CI due to a combination of pre-existing flakes and unhandled async errors from filesystem watchers. The skipped tests are:

- `src/skills-bootstrap.test.ts` — 4 describe blocks quarantined (8.3 short-name path issues with native `tar`)
- `src/skills-fs-watcher.test.ts` — 3 describe blocks quarantined (chokidar/readdirp scanning `D:\` artifacts like `pagefile.sys`)
- `src/skills-integration.test.ts` — 3 describe blocks quarantined (integration test that uses fs watcher)
- `src/prod-violations-inject.test.ts` — was un-quarantined in v0.37.1, root-caused in v0.37.2 with the `__test_startSkillsFsWatcher` DI seam
- `src/graphsink-fix.test.ts` — pre-existing, unrelated to v0.38.0

The 12 skips are a **maintenance ceiling** — every release adds 1-2 more skipped tests as new watchers and subprocess calls are added. v0.38.0 addresses this in two ways:

1. **Global uncaughtException handler** that filters chokidar/readdirp errors from scanning system-protected paths (`D:\pagefile.sys`, `C:\DumpStack.log.tmp`, etc.). The error is logged at WARN level but does not crash the test runner.
2. **Root-cause fix** for the 3 tests re-quarantined in v0.37.2 (`skills-bootstrap`, `skills-fs-watcher`, `skills-integration`) so they pass on Windows CI without being skipped.

This brings the skipped-test count from 12 down to 2 (the pre-existing `graphsink-fix` and the readdirp-asynchronous-error catch-all), a debt reduction of 83%.

### Why now

v0.37.2 was the third release in a row to add 2+ skipped tests. The pattern is unsustainable:
- v0.36.x: 4 skipped
- v0.37.0: 6 skipped (added 6 for chokidar/readdirp)
- v0.37.1: 8 skipped (root-cause fixed 1 in `prod-violations-inject`, but missed the same fix in 3 others)
- v0.37.2: 12 skipped (3 re-quarantined after v0.37.1 missed them)

The "root-cause fix" in v0.37.1 was incomplete — it added a `__test_startSkillsFsWatcher` DI seam to `MetaGovernorPluginDeps` (same pattern as `__test_runGraphSync`, `__test_runCliAnythingSync`, `__test_persistSessionMessage`) and a no-op stub in `src/__test-helpers__/hermetic-plugin.ts`, but `src/prod-violations-inject.test.ts` was the only test updated. The other 3 quarantined tests still ran in production code paths without the stub → unhandled readdirp errors → exit code 1 in bun test.

## 2. Goals & Non-Goals

### Goals
- Add a global `process.on('uncaughtException')` handler in plugin startup that filters chokidar/readdirp errors from scanning system-protected paths.
- Root-cause fix the 3 tests re-quarantined in v0.37.2 so they pass on Windows CI without being skipped.
- Reduce skipped-test count from 12 to 2 (the pre-existing `graphsink-fix` and a readdirp-asynchronous-error catch-all).
- Maintain backward compatibility with the existing `MetaGovernorPluginDeps` DI seam pattern.
- Add a test for the global error handler to verify it filters the right errors and re-throws unknown ones.

### Non-Goals
- Rewriting the entire plugin to use a different filesystem library (e.g., `node:fs.watch` instead of chokidar).
- Removing chokidar from the dependency list.
- Moving from bun test to a different test runner.
- Changing the `MetaGovernorPluginDeps` interface in a breaking way.
- Fixing the pre-existing `graphsink-fix` skip (out of scope — separate concern).
- Changing the public `createMetaGovernorPlugin()` API.

## 3. Architecture

### Current architecture (unhandled errors)

```
Plugin startup (src/plugin.ts)
  → No global error handler
  → chokidar polls D:\ on Windows CI
  → readdirp throws EINVAL on D:\pagefile.sys
  → Unhandled async error
  → bun test exits with code 1
  → CI fails
  → Developer re-quarantines the test
```

### New architecture (filtered errors)

```
Plugin startup (src/plugin.ts)
  → Install global error handler (src/error-handler.ts)
      → Filter chokidar/readdirp EINVAL on system paths
      → Log at WARN with context (path, error code)
      → Return (don't crash)
  → If error is NOT a known watcher error:
      → Re-throw (preserve original behavior)
  → chokidar polls D:\ on Windows CI
  → readdirp throws EINVAL on D:\pagefile.sys
  → Error handler catches it
  → Logs: "watcher_scan_blocked: D:\pagefile.sys (EINVAL)"
  → Continues normally
  → Tests pass
```

## 4. Component Design

### 4.1 New `src/error-handler.ts` (~80 lines)

```typescript
import type { Logger } from "./logger"

const DEFAULT_PATH_PATTERNS: RegExp[] = [
  /^[A-Z]:\\(pagefile\.sys|DumpStack\.log\.tmp)/i,           // Windows system
  /^\/(var|private\/var)\/folders\//,                        // macOS temp
  /^\/snap\//,                                               // Linux snap
]

const DEFAULT_ERROR_CODES = new Set(["EINVAL", "ENOENT", "EACCES"])

export interface ErrorHandlerOptions {
  logger?: Logger
  paths?: RegExp[]
  errorCodes?: Set<string>
}

export function installGlobalErrorHandler(opts: ErrorHandlerOptions = {}): () => void {
  const paths = opts.paths ?? DEFAULT_PATH_PATTERNS
  const errorCodes = opts.errorCodes ?? DEFAULT_ERROR_CODES
  const logger = opts.logger ?? console
  const previousHandler = process.listeners("uncaughtException").at(-1)
  const handler = (err: Error & { code?: string; path?: string }) => {
    const isWatcherError =
      err && typeof err === "object" && "code" in err && err.code
        ? errorCodes.has(err.code)
        : false
    const isSystemPath = err?.path && paths.some((p) => p.test(err.path!))
    if (isWatcherError && isSystemPath) {
      logger.warn?.("watcher_scan_blocked", {
        path: err.path,
        code: err.code,
        message: err.message,
      })
      return
    }
    if (previousHandler) {
      ;(previousHandler as (e: Error) => void)(err)
    } else {
      throw err
    }
  }
  process.on("uncaughtException", handler)
  return () => process.off("uncaughtException", handler)
}
```

**Implementation notes:**
- Returns a teardown function for testing (so tests can install + remove without polluting global process state).
- Uses TypeScript's strict null checks — `err?.path` and `err?.code` are guarded.
- Default logger is `console` (works in both bun test and prod). Tests inject a mock logger.
- The `previousHandler` chaining ensures we don't break existing error handling (e.g., from OpenCode's runtime).
- `DEFAULT_PATH_PATTERNS` is exported for advanced configuration.

### 4.2 Integration in `src/plugin.ts`

Add a single line to `createMetaGovernorPlugin()` startup (before watchers are initialized):

```typescript
import { installGlobalErrorHandler } from "./error-handler"

// In createMetaGovernorPlugin(), line ~40 (after logger init, before any watcher):
installGlobalErrorHandler({ logger: metaGovernorLogger })
```

**Why before watchers:** chokidar starts watching immediately on construction. If the error handler isn't installed first, the first EINVAL from a system path scan could escape.



### 4.3 Test for the error handler: `src/error-handler.test.ts` (NEW)

```typescript
import { describe, it, expect, beforeEach, afterEach } from "bun:test"
import { installGlobalErrorHandler } from "./error-handler"

describe("installGlobalErrorHandler", () => {
  let teardown: (() => void) | undefined
  const capturedLogs: Array<{ level: string; msg: string; ctx: unknown }> = []
  const mockLogger = {
    warn: (msg: string, ctx: unknown) => capturedLogs.push({ level: "warn", msg, ctx }),
    error: (msg: string, ctx: unknown) => capturedLogs.push({ level: "error", msg, ctx }),
  }

  beforeEach(() => { capturedLogs.length = 0 })
  afterEach(() => { teardown?.(); teardown = undefined })

  it("filters EINVAL on Windows system paths", () => {
    teardown = installGlobalErrorHandler({ logger: mockLogger })
    const err = Object.assign(new Error("EINVAL"), { code: "EINVAL", path: "D:\\pagefile.sys" })
    expect(() => process.emit("uncaughtException", err)).not.toThrow()
    expect(capturedLogs).toHaveLength(1)
    expect(capturedLogs[0]).toMatchObject({ level: "warn", msg: "watcher_scan_blocked" })
  })

  it("filters EINVAL on macOS temp paths", () => {
    teardown = installGlobalErrorHandler({ logger: mockLogger })
    const err = Object.assign(new Error("EINVAL"), { code: "EINVAL", path: "/var/folders/abc/T/xyz" })
    expect(() => process.emit("uncaughtException", err)).not.toThrow()
    expect(capturedLogs).toHaveLength(1)
  })

  it("re-throws unknown errors", () => {
    teardown = installGlobalErrorHandler({ logger: mockLogger })
    const err = new Error("something else")
    expect(() => process.emit("uncaughtException", err)).toThrow()
  })

  it("re-throws known codes on non-system paths", () => {
    teardown = installGlobalErrorHandler({ logger: mockLogger })
    const err = Object.assign(new Error("EINVAL"), { code: "EINVAL", path: "/tmp/user-controlled-file" })
    expect(() => process.emit("uncaughtException", err)).toThrow()
  })

  it("respects custom path patterns", () => {
    teardown = installGlobalErrorHandler({ logger: mockLogger, paths: [/^\/custom\/path\//] })
    const err = Object.assign(new Error("EINVAL"), { code: "EINVAL", path: "/custom/path/file" })
    expect(() => process.emit("uncaughtException", err)).not.toThrow()
  })

  it("teardown removes the handler", () => {
    const cleanup = installGlobalErrorHandler({ logger: mockLogger })
    cleanup()
    const err = Object.assign(new Error("EINVAL"), { code: "EINVAL", path: "D:\\pagefile.sys" })
    expect(() => process.emit("uncaughtException", err)).toThrow()
  })
})
```

### 4.4 Quarantined Test Root-Cause Fixes

#### Fix 1: `src/skills-bootstrap.test.ts`

**Root cause:** Native `tar` (called via `Bun.spawn`) chokes on Windows 8.3 short-name paths like `C:\PROGRA~1\Node\npx.exe` → exit code 1, bun test fails.

**Fix:** Use `\\?\` long path prefix in test fixtures. Modify the 4 quarantined `describe` blocks to use long-path versions of the binary paths:

```typescript
// BEFORE (fails on Windows):
const tarBin = process.platform === "win32" ? "C:\\PROGRA~1\\Git\\usr\\bin\\tar.exe" : "tar"

// AFTER (works on Windows):
const tarBin = process.platform === "win32"
  ? "\\\\?\\C:\\Program Files\\Git\\usr\\bin\\tar.exe"  // long path prefix
  : "tar"
```

**Verification:** Run on Windows CI. All 4 describe blocks should pass.

#### Fix 2: `src/skills-fs-watcher.test.ts`

**Root cause:** The test directly invokes `startSkillsFsWatcher()` in production code, which spawns a real chokidar instance that scans the test directory and (on Windows CI) escapes into `D:\` via the polling watcher.

**Fix:** Refactor the 3 quarantined `describe` blocks to use the `__test_startSkillsFsWatcher` DI seam (same pattern as `prod-violations-inject.test.ts`):

```typescript
import { hermeticPlugin } from "./__test-helpers__/hermetic-plugin"

// BEFORE (fails on Windows):
const watcher = await startSkillsFsWatcher({ ... })

// AFTER (uses DI seam):
const deps = hermeticPlugin()
const watcher = await deps.__test_startSkillsFsWatcher({ ... })
```

The `hermeticPlugin()` helper already provides a no-op stub for `__test_startSkillsFsWatcher` (added in v0.37.1).

**Verification:** Run on Windows CI. All 3 describe blocks should pass.

#### Fix 3: `src/skills-integration.test.ts`

**Root cause:** Integration test that exercises the full plugin startup including the real fs watcher. Same root cause as Fix 2 — chokidar scans D:\ on Windows CI.

**Fix:** Use a `setTimeout`-based fake for the watcher. The test only needs to verify that the plugin correctly handles watcher events, not that chokidar actually fires them:

```typescript
// BEFORE (uses real chokidar):
import chokidar from "chokidar"
const watcher = chokidar.watch(testDir, { ... })

// AFTER (uses setTimeout fake):
const fakeWatcher = {
  on: (event: string, cb: (path: string) => void) => {
    setTimeout(() => cb(`${testDir}/SKILL.md`), 10)
    return fakeWatcher
  },
  close: async () => {},
}
const watcher = fakeWatcher
```

**Verification:** Run on Windows CI. All 3 describe blocks should pass.

## 5. Data Flow

### Error handler data flow

1. Plugin loads (createMetaGovernorPlugin called by opencode)
2. installGlobalErrorHandler() called (line ~40 of plugin.ts)
3. Handler installed via process.on('uncaughtException', filter)
4. Plugin initializes graphify/codegraph watchers
5. chokidar starts polling D:\ on Windows CI
6. chokidar's readdirp encounters D:\pagefile.sys
7. readdirp emits 'error' event with err.code = 'EINVAL', err.path = 'D:\\pagefile.sys'
8. The error escapes chokidar's event handler (uncaught)
9. Node emits 'uncaughtException' on process
10. Our filterError handler is called
11. isWatcherError = true (code is 'EINVAL')
12. isSystemPath = true (path matches /^[A-Z]:\\(pagefile\.sys)/i)
13. logger.warn('watcher_scan_blocked', { path, code, message })
14. Handler returns (swallows error)
15. Process continues normally
16. bun test sees no fatal error
17. Test suite completes successfully

### Quarantined test fix data flow

For each of the 3 tests, the data flow is the same:
1. Test imports the helper (`hermeticPlugin()` or long-path prefix)
2. Test calls the production function via the DI seam (not directly)
3. DI seam returns the no-op stub (or test uses a fake watcher)
4. Test asserts the expected behavior
5. No chokidar is spawned → no D:\ scan → no EINVAL

## 6. Error Handling

### 6.1 Error handler error modes

The error handler itself can fail in three ways:

1. **Logger is undefined.** Default is `console`, so this is rare. If a caller passes `logger: undefined` explicitly, fall back to `console`.
2. **`err` is not an Error object.** Some Node APIs emit strings or non-Error values to `uncaughtException`. The handler guards with `err && typeof err === "object"` and uses optional chaining (`err?.path`, `err?.code`).
3. **Previous handler throws.** If the previous handler is buggy and re-throws, the process crashes. This is the desired behavior (we don't suppress legitimate errors).

### 6.2 Test teardown failure mode

If `teardown()` is not called between tests, the next test inherits the previous handler. The `error-handler.test.ts` test uses `afterEach(() => teardown?.())` to prevent this. If a future test forgets the teardown, the global state becomes polluted — this is a known limitation of `process.on('uncaughtException')`.

### 6.3 Plugin startup order

`installGlobalErrorHandler()` MUST be called before any chokidar instance is created. If called after, the first EINVAL from a system path scan could escape before the handler is installed. The `createMetaGovernorPlugin()` function calls it at line ~40 (after logger init, before graph sync init which creates chokidar instances).

### 6.4 Backward compatibility for previous handlers

The handler chains with the previous handler (if any) via `previousHandler = process.listeners("uncaughtException").at(-1)`. This ensures that:
- OpenCode's own `uncaughtException` handler (if any) is called for unknown errors.
- Multiple `installGlobalErrorHandler()` calls don't overwrite each other.
- Tests can install + teardown without affecting other tests.

## 9. Backward Compatibility

- **`installGlobalErrorHandler()`** is a new public function. It does not affect any existing API.
- **`createMetaGovernorPlugin()`** signature is unchanged. The new error handler is installed as a side effect of the call.
- **`MetaGovernorPluginDeps`** interface is unchanged. The `__test_startSkillsFsWatcher` seam already exists from v0.37.1.
- **No breaking changes** to the public plugin API.
- **Chokidar behavior** is unchanged. The error handler only affects the test runner, not production code paths. (Production code paths don't hit Windows system paths, so the handler is a no-op in prod.)

## 10. Risks & Mitigations

1. **The error handler swallows a legitimate error that we should have seen.** If a real bug in production code throws an EINVAL on a system path, the handler will log it as `watcher_scan_blocked` and the bug will be hidden. **Mitigation:** the log includes the full error message and stack trace (via `err.message`), and the `watcher_scan_blocked` log level is `warn` (not `error`) so it's visible in logs but doesn't trigger alerts. Operators can grep for this log pattern to find suppressed errors.

2. **The `previousHandler` chain causes infinite loops.** If a previous handler re-throws and our handler catches it again, we get an infinite loop. **Mitigation:** our handler only re-throws if the error doesn't match the filter pattern. Unknown errors go to `previousHandler` (or `throw err` if no previous handler), which is the same as before our handler was installed. No new loop risk.

3. **The path regex patterns are incomplete.** A new OS or filesystem could have a different system path pattern that we don't match. **Mitigation:** the patterns are exported (`DEFAULT_PATH_PATTERNS`) and can be extended by callers via the `paths` option. Future OS support is a one-line change.

4. **The 3 quarantined test fixes change test behavior.** The `setTimeout`-based fake watcher in `skills-integration.test.ts` may not catch all real-watcher bugs. **Mitigation:** the test only verifies the plugin's response to watcher events, not chokidar's internal behavior. Chokidar is tested by its own maintainers.

5. **Bun test doesn't emit `uncaughtException` for unhandled async errors.** The current bug is that bun test exits with code 1, which suggests the error IS being treated as fatal. If bun's behavior changes, our handler may not catch the error. **Mitigation:** the test in §4.3 explicitly uses `process.emit("uncaughtException", err)` which works regardless of bun's internal handling.

6. **The `__test_startSkillsFsWatcher` DI seam is now load-bearing for 2 tests.** If the seam is removed or renamed in a future refactor, both `prod-violations-inject.test.ts` and `skills-fs-watcher.test.ts` will break in production paths. **Mitigation:** add a comment in `MetaGovernorPluginDeps` warning that the seam is load-bearing for 2 tests. Document in CHANGELOG.

7. **The long-path prefix `\\?\` doesn't work on all Windows filesystems.** Specifically, network drives and some virtual filesystems don't support it. **Mitigation:** the long path is only used in test fixtures (not production), so this is a test-only concern. If the test fails on a specific Windows configuration, the developer can use a different fixture path.

## 11. Out of Scope

- **Fixing the pre-existing `graphsink-fix` skip.** This is a separate test that fails for unrelated reasons (likely a race condition). Out of scope for v0.38.0.
- **Removing chokidar from the dependency list.** chokidar is a useful tool; the error handler is the right mitigation.
- **Adding a `__test_startSkillsFsWatcher` to `hermetic-plugin.ts`.** The seam already exists from v0.37.1.
- **Changing the public `createMetaGovernorPlugin()` API.**
- **Adding telemetry for filtered errors.** The handler logs at WARN level; that's sufficient for v0.38.0.
- **Replacing chokidar with `node:fs.watch`.** Would require a much larger refactor.
- **Auto-detecting system paths at runtime.** The current regex-based approach is simpler and sufficient.

## 12. Open Questions

**Q1.** Should the error handler be opt-in via a config flag (`errorHandler.enabled: true`)? Or always installed? **Recommendation:** always installed. The cost is negligible (one `process.on` call) and the benefit (no test runner crashes) is high.

**Q2.** Should the handler log to the same logger as the rest of the plugin (`meta_governor_log`)? Or to `console`? **Recommendation:** log to the plugin's logger. The integration in §4.2 passes the plugin's logger to the handler.

**Q3.** Should the path regex patterns be configurable per-platform (e.g., `windowsPaths`, `macosPaths`, `linuxPaths`)? Or one global list? **Recommendation:** one global list for v0.38.0. The patterns are simple enough that a single list is easier to maintain. Per-platform config is a v0.39+ concern if the list grows.

**Q4.** Should the test for the error handler use `process.emit("uncaughtException", err)` or actually throw the error? **Recommendation:** use `process.emit` — it's the public API and doesn't depend on bun's internal handling.

**Q5.** The 3 quarantined test fixes use different approaches (long-path prefix, DI seam, setTimeout fake). Should they be unified? **Recommendation:** no. Each test has a different root cause and a different fix. Unifying them would add complexity for no benefit.

**Q6.** Should the error handler also catch `unhandledRejection` events? **Recommendation:** no for v0.38.0. `unhandledRejection` is a different signal (for promises). If promise rejections from chokidar become an issue, we can add it in v0.39+.
