# v0.38.0 — CI/CD Infrastructure Design Spec

**Date:** 2026-08-28
**Target version:** 0.38.0
**Scope:** CI/CD infrastructure only (no runtime plugin logic changes)
**Author:** design-only (no implementation in this PR)

---

## 1. Overview / Context

We just shipped **v0.37.2** (manual release on 2026-08-28, see `CHANGELOG.md`
top entry). The release exposed three concrete pains in our shipping
pipeline that are now blocking velocity:

1. **Schema-vs-runtime drift in the OTHER direction.** v0.37.2 was
   *almost entirely* a fix for the *committed asset ↔ generator* drift
   (added `src/generate-schema-sync.test.ts` to pin them byte-for-byte).
   That test catches drift when someone edits `src/generate-schema.ts`
   without bumping the committed JSON, or vice-versa. **It does NOT
   catch the parallel drift where someone adds a field to
   `MetaGovernorPluginConfig` in `src/config.ts` and forgets to update
   either `src/generate-schema.ts` or the committed
   `assets/omo-meta-governor.schema.json`.** Every previous drift
   incident (v0.25.0 ciMonitor, v0.18.0 message templates, v0.22.0
   graphSync additions) had exactly that pattern: runtime added, schema
   forgotten.

2. **Windows CI flakes poison the merge gate.** `.github/workflows/ci.yml`
   has three jobs (`test`, `test-macos`, `test-windows`), all
   `continue-on-error: false`. The Windows job has historically
   contained at least two flaky tests (`readdirp Windows flake`,
   `graphsink-fix`) — they pass on macOS/Linux but fail intermittently
   on `windows-latest`. Because all three jobs gate the same PR, a
   single Windows flake can block an otherwise-green change. v0.37.2
   shipped with "2 skip" in the test report specifically to quarantine
   these.

3. **The release flow is a hand-typed shell pipeline.** `AGENTS.md`
   §3-§4 prescribe the manual sequence: `npm publish` → `git tag
   v<version>` → `git push --tags` → `gh release create v<version>
   --notes "..."`. v0.37.2 ran into PowerShell backtick escaping inside
   the `--notes` double-quoted string (`gh release create` choked on a
   backtick in the markdown body), forcing an interactive retry. This
   is the third release in a row where shell quoting has cost real
   time.

**v0.38.0** addresses all three with a small, self-contained CI/CD
infrastructure change: a new test that catches runtime→schema drift, a
quarantined Windows-only CI job, and a TypeScript release script that
replaces the hand-typed shell pipeline.

## 2. Goals & Non-Goals

### WILL (in scope for v0.38.0)

- **G1.** Add a schema contract test that walks every key in the
  `MetaGovernorPluginConfig` interface (defined in `src/config.ts:25`)
  and asserts each key has a corresponding entry in
  `assets/omo-meta-governor.schema.json`. This is the **reverse** of
  the existing `src/generate-schema-sync.test.ts` — that test pins the
  generator against the committed asset; this one pins the runtime
  against both. See §4.1.
- **G2.** Add a new CI job `test-windows-flaky` that runs ONLY the
  previously-quarantined tests (currently the `readdirp` Windows flake
  + `graphsink-fix`). This job sets `continue-on-error: true` at the
  job level so a flake never blocks a merge. See §4.2.
- **G3.** Add a `bun run release` script (`scripts/release.ts`) that
  automates the AGENTS.md §3-§4 pipeline: validate CHANGELOG → bump
  `package.json` version → run tests → run build → `npm publish` → git
  tag → `git push --tags` → `gh release create` with `--notes-file`
  (no shell escaping). Idempotent (skip if already published). Aborts
  on any step failure, leaving no half-shipped state. See §4.3.

### WILL NOT (explicit non-goals)

- **N1.** Replace the existing 3 CI jobs in `.github/workflows/ci.yml`
  (`test`, `test-macos`, `test-windows`). The new flaky job is
  *additive*.
- **N2.** Change the publishing registry. `package.json:41-44` already
  pins `publishConfig.registry = https://registry.npmjs.org/`. The
  release script honors this verbatim.
- **N3.** Replace `src/generate-schema.ts` (the hand-written
  generator). The parallel "schema autogen" project is migrating to
  `ts-json-schema-generator`; v0.38.0's contract test must work
  against *whichever* generator is current (hand-written or
  `ts-json-schema-generator`-driven).
- **N4.** Auto-merge the new flaky job into the green job once the
  flakes are fixed. That's a follow-up; the contract is that the job
  stays additive until someone deletes the workflow file.
- **N5.** Replace `.github/workflows/publish.yml`. That workflow
  handles tag-push → release (post-publish). The new release script
  runs *locally* (or in CI via `workflow_dispatch` in a future
  version) and complements `publish.yml`.

## 3. Architecture

### 3.1 Test placement — new file, alongside the existing sync test

- **New file:** `src/generate-schema-contract.test.ts` (alongside the
  existing `src/generate-schema-sync.test.ts:1`).
- The existing `generate-schema-sync.test.ts` enforces:
  `generator ↔ committed asset` (byte-for-byte).
- The **new** `generate-schema-contract.test.ts` enforces:
  `runtime interface ↔ committed asset` (key presence + type
  compatibility, no byte-equality).

These two tests are complementary, not duplicates:
- If a dev edits `src/generate-schema.ts` without re-running
  `bun run build`, both tests fail.
- If a dev edits `src/config.ts` without re-running `bun run build`,
  *only* the new contract test fails — which is exactly what v0.38.0
  is for.

### 3.2 CI workflow structure — new file, not a modification

- **New file:** `.github/workflows/test-windows-flaky.yml`.
- Lives alongside `.github/workflows/ci.yml:1` (3-job matrix) and
  `.github/workflows/publish.yml:1` (tag-push release). Modifying
  `ci.yml` would require touching the file's "stable contract" (the
  three-job matrix is referenced in `AGENTS.md`'s CI Verification Loop).
- The new file triggers on the same conditions as `ci.yml` (`push` to
  `main`, `pull_request` to `main`) and runs on `windows-latest`.
- It runs `bun test` with a *test-name filter* that matches ONLY the
  quarantined tests (e.g., `bun test -t "readdirp"` for the
  `readdirp` test file).

### 3.3 Release script entry point

- **New file:** `scripts/release.ts` (top-level `scripts/` directory
  does not exist yet — see §8).
- **Wired via** `package.json:45` `scripts` field — add
  `"release": "bun scripts/release.ts"`.
- **Invocation:** `bun run release <version>` (e.g., `bun run release
  0.38.0`). Validates `semver` shape, aborts if invalid.
- **Lives next to** `build.ts:1` (also `bun build.ts` from
  `package.json:46`), establishing a "scripts are TS files at repo
  root or under `scripts/`" convention.

## 4. Component Design

### 4.1 Schema contract test

**File:** `src/generate-schema-contract.test.ts`

**Purpose:** Catch drift where a field is added to
`MetaGovernorPluginConfig` (`src/config.ts:25`) but the schema
(`assets/omo-meta-governor.schema.json`) is not regenerated.

**Walking the interface.** Two implementation options were considered:

- **Option A — TypeScript Compiler API (`ts.createProgram` +
  `checker.getTypeAtLocation`).** This is the heavyweight approach.
  Requires `typescript` as a runtime dep (already in `devDependencies`,
  `package.json:17`).
- **Option B — Drive via the existing `ts-json-schema-generator` dep
  that the parallel schema-autogen project is adding.** This generates
  a *fresh* schema at test time directly from the interface, then
  compares its key set against the committed asset.

**Decision: Option B.** Constraints from the task brief explicitly
say *"don't propose a separate TS-compiler dep"*, and the parallel
schema-autogen project is already adding `ts-json-schema-generator`
to `devDependencies`. Reusing it here means:

1. The contract test does not duplicate the generator's job — it
   re-generates, then compares key sets.
2. If/when the generator migrates from the hand-written
   `src/generate-schema.ts` to `ts-json-schema-generator`, this test
   automatically follows without modification.
3. Single source of schema truth at test time matches the single
   source of schema truth at build time (both produce the same shape
   from the same interface).

**Algorithm (pseudocode):**

```text
1. const cfgSrc = readFileSync("src/config.ts", "utf8")
2. const cfgKeys = extractMetaGovernorConfigKeys(cfgSrc)
     // Simple recursive regex extractor OR ts-json-schema-generator
     // "getSymbols" output. Either is fine; document which we use.
3. const schema = JSON.parse(readFileSync("assets/omo-meta-governor.schema.json", "utf8"))
4. for each path in cfgKeys (e.g., "enabled", "decision.maxHistoryPerSession"):
       assert schema has matching path
       (e.g., schema.properties.enabled !== undefined
        && schema.properties.decision.properties.maxHistoryPerSession !== undefined)
5. for each schema-only key not in cfgKeys:
       fail with "schema exposes runtime-missing key: <path>" (catches dead keys too)
```

**Where to put it.** `src/generate-schema-contract.test.ts` —
alongside `src/generate-schema.test.ts:1` and
`src/generate-schema-sync.test.ts:1`. Naming follows the existing
`<module>.test.ts` convention used across `src/`.

**What it asserts (per `describe` block):**

| Block | Asserts |
|-------|---------|
| `runtime -> schema coverage` | Every interface key in `MetaGovernorPluginConfig` exists at the matching path in the committed schema. |
| `schema -> runtime coverage` | Every committed schema property exists in the runtime interface (catches orphaned/dead keys). |
| `leaf types match` | For each shared leaf (e.g., `decision.maxHistoryPerSession: number`), the schema's `type` (or `oneOf`/`enum`) is compatible with the TypeScript type. |
| `interface-level invariants` | `additionalProperties: false` at every nested object (the existing generator enforces this; the contract test guards it from being lost on a generator migration). |

**Note on the nested-key walk.** `MetaGovernorPluginConfig` is one
level deep in most places (`enabled`, `decision`, `memory`, …) but
nested two levels deep in places like
`decision.warnMessageTemplate`. The contract test must recursively
descend nested objects and compare full dotted paths.
### 4.2 Separate CI flaky job

**File:** `.github/workflows/test-windows-flaky.yml`

**Triggers:** identical to `.github/workflows/ci.yml:4-7`:

```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
```

**Job definition (sketch):**

```yaml
name: test-windows-flaky

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test-windows-flaky:
    # The single point of failure for flaky Windows tests.
    # Continue-on-error at the job level keeps the merge green while
    # we triage these.
    continue-on-error: true
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v5
      - uses: oven-sh/setup-bun@v2
        with:
          bun-version: 1.3.14
      - run: bun install
      - run: bun run typecheck
      # -t flag filters by test-name substring. Adjust as flakes move.
      - name: Run quarantined tests
        run: |
          bun test src/readdirp.test.ts
          bun test src/graphsink-fix.test.ts
```

**Why a separate file, not a job inside `ci.yml`?** Two reasons:

1. **Isolation of flaky signal.** `ci.yml`'s `test-windows` job has
   `continue-on-error: false` (implicit — that's the default). Changing
   *that* job's flake tolerance would silently make every other
   Windows test non-blocking too. A separate file scopes the
   `continue-on-error: true` to the quarantined tests only.
2. **Independent evolution.** When the flakes are fixed, we delete
   the quarantined `.test.ts` files (or move them back into the main
   suite), then delete `.github/workflows/test-windows-flaky.yml`
   entirely. No surgery on `ci.yml` required.

**Why `continue-on-error: true` at the job level (not per-step)?**
Per-step `continue-on-error` would let downstream steps run after a
test failure, which is pointless (there's nothing downstream to run).
Job-level is correct: a flake here surfaces a yellow/red badge on this
workflow but does not block any merge.

**Quarantined tests to include (as of v0.37.2):**

- `src/readdirp.test.ts` (Windows-specific readdirp flake — referenced
  in `README.md` "Known flaky test" section)
- `src/graphsink-fix.test.ts` (pre-existing quarantine)

A list at the top of the workflow file (with one-line rationale per
entry) makes it auditable. New quarantines are added by appending one
line + one `bun test` step.

### 4.3 Release script

**File:** `scripts/release.ts`

**Top-level shape:**

```typescript
#!/usr/bin/env bun
/**
 * scripts/release.ts — v0.38.0 release automation.
 * Replaces the manual AGENTS.md §3-§4 pipeline with a typed, idempotent
 * sequence. Aborts on any step failure; leaves no half-shipped state.
 */

import { $ } from "bun"
import { readFile, writeFile } from "node:fs/promises"
import { spawn } from "bun"

const SEMVER = /^\d+\.\d+\.\d+(-[a-z0-9.-]+)?$/i

async function step(name: string, fn: () => Promise<void>): Promise<void> {
  process.stdout.write(`\n→ ${name}\n`)
  await fn()
  process.stdout.write(`  ✓ ${name}\n`)
}

async function main() {
  const version = process.argv[2]
  if (!version || !SEMVER.test(version)) {
    console.error(`usage: bun run release <semver-version>`)
    process.exit(2)
  }

  // Step 1: validate CHANGELOG entry exists for this version
  await step("validate CHANGELOG.md entry", async () => {
    const changelog = await readFile("CHANGELOG.md", "utf8")
    const header = `## [${version}]`
    if (!changelog.includes(header)) {
      throw new Error(`CHANGELOG.md missing entry for ${header}. Add it before releasing.`)
    }
    // Per AGENTS.md §3, the entry MUST include the ship-protocol section.
    if (!/### Ship protocol compliance/i.test(changelog)) {
      throw new Error(`CHANGELOG.md entry for ${version} is missing "Ship protocol compliance" section.`)
    }
    // The brief specifies ✅. Look for the literal emoji marker.
    if (!changelog.match(/[\u2705\u2713\u2714]|:white_check_mark:|Ship protocol compliance/)) {
      // Soft warning only — don't abort. AGENTS.md §3 wording varies.
      console.warn("  ! could not find ✅ in CHANGELOG — verify manually.")
    }
  })

  // Step 2: idempotency guard — check if version is already published
  await step(`check npm registry for ${version}`, async () => {
    const proc = spawn({
      cmd: ["npm", "view", "@herjarsa/omo-meta-governor", "version"],
      stdout: "pipe",
      stderr: "pipe",
    })
    const out = await new Response(proc.stdout).text()
    const latest = out.trim()
    if (latest === version) {
      console.log(`  ↺ version ${version} already published — idempotent no-op`)
      process.exit(0)
    }
  })

  // Step 3: bump package.json
  await step(`bump package.json to ${version}`, async () => {
    const pkg = JSON.parse(await readFile("package.json", "utf8"))
    pkg.version = version
    await writeFile("package.json", JSON.stringify(pkg, null, 2) + "\n")
  })

  // Step 4: tests + build
  await step("run tests", () => $`bun test`.quiet())
  await step("run build", () => $`bun run build`.quiet())

  // Step 5: publish (fail-closed)
  await step("npm publish", () => $`npm publish --access public --provenance`.quiet())

  // Step 6: git tag + push (only after publish succeeds)
  await step(`git tag v${version}`, () => $`git tag v${version}`.quiet())
  await step("git push --tags", () => $`git push --tags`.quiet())

  // Step 7: gh release with --notes-file (no shell escaping)
  await step(`gh release create v${version}`, async () => {
    // Extract just this version's section to a temp file so the
    // GitHub release body is scoped to this version, not the whole log.
    const fullChangelog = await readFile("CHANGELOG.md", "utf8")
    const section = extractVersionSection(fullChangelog, version)
    const tmpPath = `.release-notes-v${version}.md`
    await writeFile(tmpPath, section)
    try {
      await $`gh release create v${version} --repo herjarsa/omo-meta-governor --title v${version} --notes-file ${tmpPath}`.quiet()
    } finally {
      // Clean up the temp file. Idempotent.
      await $`rm -f ${tmpPath}`.nothrow()
    }
  })

  console.log(`\n✓ Released v${version}`)
}

function extractVersionSection(changelog: string, version: string): string {
  // Find "## [<version>]" header, take everything until next "## [" header.
  const headerRe = new RegExp(`^## \\[${version.replace(/\./g, "\\.")}\\]`, "m")
  const match = changelog.match(headerRe)
  if (!match || match.index === undefined) return changelog
  const start = match.index
  const after = changelog.slice(start)
  const nextHeader = after.slice(1).search(/^## \[/m)
  const end = nextHeader === -1 ? changelog.length : start + 1 + nextHeader
  return changelog.slice(start, end).trim() + "\n"
}

main().catch((err) => {
  console.error(`\n✗ release failed: ${err?.message ?? err}`)
  process.exit(1)
})
```

**Error handling per step:**

| Step | On failure |
|------|-----------|
| 1 (validate CHANGELOG) | `process.exit(1)` — never publish without an entry. |
| 2 (idempotency check) | If `npm view` errors (network down), abort. If version already matches, `process.exit(0)` (success no-op). |
| 3 (bump version) | Abort. `package.json` is mutated, but `git diff` is uncommitted so it's harmless to leave. |
| 4 (tests + build) | Abort. Re-run locally; do NOT auto-fix. |
| 5 (npm publish) | Abort. No tag, no release, no `git push --tags`. **Critical invariant.** |
| 6 (tag + push) | Abort. We've published but not tagged — manual fixup; the script exits non-zero and prints the partial state. |
| 7 (gh release) | Tag exists; release does not. Manual: `gh release create ...` retry. Script prints the temp notes file path so the operator can recover without losing context. |

**Idempotency strategy:**

- **Primary guard:** the npm registry version check in step 2 — if
  `npm view @herjarsa/omo-meta-governor version` already equals the
  requested version, exit success without doing anything.
- **Secondary guards (per step):**
  - `npm publish` is naturally idempotent for the same version (npm
    rejects re-publishes of an existing version).
  - `git tag v<X.Y.Z>` is idempotent (creating an existing tag is a
    no-op; `--force` not used).
  - `gh release create` for an existing tag fails with a clear error
    — the operator can manually retry with `--notes-file`.

**Why `Bun.spawn` / `bun $` instead of shelling out from Node?**

- The `package.json:51` `"type": "module"` and the existing
  `build.ts:1` (`#!/usr/bin/env bun`) establish Bun as the runtime.
- `await $\`...\`` (Bun shell) auto-quotes args, eliminating the
  PowerShell backtick issue that motivated this script.
- `Bun.spawn` is the lower-level escape hatch for cases where we
  need stdin/stdout pipes (the `npm view` version probe).

## 6. Error Handling

### 6.1 Schema contract test

- **Field added to interface, schema not regenerated** -> test fails
  with `"runtime field 'decision.newField' is missing from schema"`.
  This is the **expected** failure mode and the *whole point* of the
  test. The fix is `bun run build` to regenerate the schema.
- **Field removed from interface, still in schema** -> test fails with
  `"schema field 'decision.removedField' is no longer in runtime"`.
  Expected failure mode; fix is `bun run build` (which regenerates the
  committed asset from the generator, dropping the dead key).
- **`ts-json-schema-generator` dep is missing** -> test fails at
  `import` time with `"Cannot find module 'ts-json-schema-generator'"`.
  This signals that the parallel schema-autogen project has not landed
  the dep yet, so v0.38.0 cannot ship until that lands first. **The
  contract test should be added in the same commit that introduces
  the dep**, OR the test should use the hand-written generator's
  `generateSchema()` output as a proxy with a TODO comment until the
  parallel project lands. (See Open Question Q2.)
- **JSON parse error on the committed asset** -> test fails with the
  parser error; this is correct (broken committed asset should fail
  CI).

### 6.2 Release script

- **`npm publish` fails** -> script exits 1 before tagging or pushing.
  Critical invariant: **no tag, no release, no remote state mutation
  past npm** if npm failed. The `package.json` bump is uncommitted, so
  `git checkout -- package.json` reverts cleanly.
- **`git push --tags` fails after `git tag`** -> script exits 1, the
  local tag exists, no release. Operator manually runs
  `git push --tags`. Idempotent: re-running the script will skip the
  npm publish (idempotency guard) and re-attempt tag push.
- **`gh release create` fails** -> script exits 1, tag exists on remote,
  npm has the version. Operator manually runs the gh step (idempotent
  on retry — gh rejects duplicate release creation but `--notes-file`
  approach lets us retry cleanly).
- **PowerShell backtick re-encounter** -> impossible by construction:
  `bun $` template literals are auto-escaped and there is no shell
  quoting of `--notes` content (we pass `--notes-file`).
- **CHANGELOG.md is missing the "Ship protocol compliance" section**
  -> step 1 fails. This is the v0.37.2 pattern: the brief specifies
  ✅ marker; we warn rather than hard-fail because the literal emoji
  has appeared in multiple encodings across recent changelogs
  (`:white_check_mark:`, `\u2705`, raw glyph). The hard contract is
  the *section header* (`### Ship protocol compliance`), not the
  marker glyph.

## 7. Testing Strategy

### 7.1 Schema contract test

- **RED proof:** Add a temporary field to a copy of
  `MetaGovernorPluginConfig` (in a test fixture, not in `src/config.ts`
  itself). Re-run the test. Assert failure message matches the
  expected `"runtime field ... missing from schema"` pattern.
- **GREEN proof:** Remove the temporary field, re-run. Assert pass.
- **Coverage proof:** Run the full test suite (`bun test`) — the
  contract test passes alongside the existing 1035 tests.

### 7.2 Release script — testable without actually publishing

The release script MUST be unit-testable without invoking npm, git, or
gh against the real world. Two approaches:

**Option a — Function decomposition.** Refactor `main()` into pure
helper functions:

- `validateChangelog(version, content): { ok: boolean; error?: string }`
  — pure.
- `extractVersionSection(changelog, version): string` — pure.
- `shouldSkipForIdempotency(currentVersion, requestedVersion): boolean`
  — pure.

These pure functions are unit-tested directly. The orchestration in
`main()` is a thin shell over these.

**Option b — Spawn mock seam.** Inject a `runner: (cmd: string[]) =>
  Promise<{ exitCode: number; stdout: string; stderr: string }>` into
  `main()` (default = `Bun.spawn`-based implementation). Tests pass a
  mock that returns canned responses for `npm view`, `npm publish`,
  `git tag`, `gh release create`, etc.

**Decision: Option a primary, Option b as needed.** The pure helpers
cover ~80% of the logic (changelog validation, idempotency check,
section extraction, error formatting). The remaining 20% (the actual
spawn sequencing) is covered by:

- A **dry-run mode** added to the script: `bun run release 0.38.0
  --dry-run` runs every step EXCEPT step 5 (`npm publish`), step 6
  (git push --tags), and step 7 (gh release). Steps 1-4 execute
  normally; steps 5-7 print `"[dry-run] would: npm publish ..."` and
  continue. This makes the script testable end-to-end without
  mutating real state, and gives operators a "preview" mode.
- A **`--steps-only validate,bump,test,build`** mode that lets a test
  harness run individual steps.

The dry-run flag is the primary test surface; the spawn mock is a
follow-up if integration coverage gaps appear.

**Test file:** `scripts/release.test.ts` (sibling to the script).
Run via `bun test scripts/release.test.ts`.

### 7.3 CI flaky job

- **Verification:** The new workflow file passes schema validation
  (`gh workflow view` after pushing).
- **Quarantine effectiveness:** Force a known-passing test into the
  quarantine list and assert the job stays green even when run on a
  branch with an unrelated red `ci.yml` job.
- **Cleanup:** Document in the workflow file header that the workflow
  file should be deleted when its test list becomes empty.

## 9. Risks & Mitigations

### Risk 1 — Release script accidentally publishes to the wrong registry

**Likelihood:** Medium. **Impact:** High (publishing to a private
registry, then re-publishing to npmjs, leaves a bad public record).

**Mitigation:**

- The script reads `publishConfig.registry` from `package.json` (line
  41-44) and asserts it equals `https://registry.npmjs.org/` before
  running `npm publish`. If it doesn't match, abort.
- The script's `npm publish` invocation uses `--registry
  https://registry.npmjs.org/` explicitly as a belt-and-suspenders
  override, regardless of `publishConfig`.
- The script refuses to run if `NPM_CONFIG_REGISTRY` is set in the
  environment to anything other than `https://registry.npmjs.org/`.
- CI invocation is `.github/workflows/publish.yml` only (which has the
  same `registry=` line at `publish.yml:39-40`); the local script is
  the operator-side path.

### Risk 2 — Schema contract test is too strict and breaks legitimate changes

**Likelihood:** Medium. **Impact:** Low (test fails, dev sees clear
error, runs `bun run build`, re-runs, passes).

**Mitigation:**

- The test asserts **presence of keys**, not **exact JSON byte
  equality**. Adding a field to the interface + running `bun run
  build` regenerates the schema; the test passes.
- Failure messages are explicit (`runtime field 'X' missing from
  schema`) so devs immediately know the fix.
- Document the test in `README.md` "Testing" section as "if you add a
  field to `MetaGovernorPluginConfig`, run `bun run build` before
  pushing".

### Risk 3 — CI flaky job never gets cleaned up

**Likelihood:** High (entropy always wins; without an owner, the job
becomes permanent dead weight). **Impact:** Medium (yellow badge noise;
slower CI dashboard; one extra Windows runner per push).

**Mitigation:**

- **Workflow file header comment** explicitly states: *"When the
  quarantined test list reaches 0 entries, delete this file."*
- **Tracking TODO:** add a `TODO(v0.40.0): audit test-windows-flaky
  job — are the quarantines still needed?` line to `CHANGELOG.md` or
  a project-level TODO file.
- **Quarterly hygiene:** the script's `bun run typecheck` and
  `bun test` steps in the new workflow use the same `bun-version:
  1.3.14` pinning as `ci.yml`, so when the main matrix bumps Bun,
  the flaky job follows automatically — but the quarantined test list
  itself requires manual review.

### Risk 4 — Release script's CHANGELOG validation rejects valid entries

**Likelihood:** Low. **Impact:** Medium (operator has to manually run
`npm publish` + `gh release create`, defeating the purpose).

**Mitigation:**

- The hard contract is the *section header*
  (`### Ship protocol compliance`), not the ✅ glyph. The brief
  specifies ✅ but recent changelogs (v0.37.2 included) vary between
  raw glyph, `\u2705`, and `:white_check_mark:`. The script warns
  softly on the glyph and hard-fails only on the section header.
- Document the exact regex in `scripts/release.ts:1` JSDoc so the
  contract is auditable.

### Risk 5 — `npm view` for the idempotency check is slow / flaky on CI

**Likelihood:** Medium (npm registry can have transient outages).
**Impact:** Low (script aborts; operator retries).

**Mitigation:**

- The script uses a 10-second timeout on the `npm view` invocation
  via `Bun.spawn({ timeout: 10_000 })`. Past 10s, treat as "couldn't
  verify idempotency" and abort with a clear message
  (`could not reach npm registry to verify idempotency — run with
  --skip-idempotency-check if you're sure the version is not yet
  published`).
- Add `--skip-idempotency-check` CLI flag for CI invocations and
  operator-driven retries where the registry probe is the blocker.

### Risk 6 — `ts-json-schema-generator` (the parallel project's dep) is not yet merged when v0.38.0 ships

**Likelihood:** Medium (the dep is being added "in the parallel schema
autogen project" per the brief). **Impact:** Medium (contract test
fails to import).

**Mitigation:**

- **Fallback:** the contract test uses `generateSchema()` from the
  hand-written `src/generate-schema.ts` as a proxy until the parallel
  project lands. This is a worse implementation (it doesn't catch
  *generator <-> interface* drift; only *interface <-> committed-asset*
  drift) but it ships v0.38.0 today.
- A `// TODO(v0.39.0): switch to ts-json-schema-generator once
  schema-autogen PR lands` comment marks the fallback.
- See Open Question Q2.

  automatically move it to the flaky job. Out of scope; manual
  curation is fine for v0.38.0.
- **Schema validation against a live `npm view` of the published
  schema.** Static-only contract test for v0.38.0.

## 11. Open Questions

**Q1.** Should `scripts/release.ts` accept the version as `0.38.0` or
`v0.38.0`? Current sketch accepts bare `0.38.0` (and prepends `v` for
the tag). Should it also accept the `v` prefix and strip it? (Probably
yes — operator ergonomics.)

**Q2.** The schema contract test wants to reuse the
`ts-json-schema-generator` dep that the parallel schema-autogen
project is adding. If that dep lands in the same v0.38.0 release, the
test uses it directly. If it lands *after* v0.38.0, the test must
fall back to `generateSchema()` from `src/generate-schema.ts` (a
slightly weaker guarantee — see Risk 6). **Resolution:** coordinate
with the schema-autogen PR author; if their PR lands first, v0.38.0
uses the new dep; otherwise, ship the fallback. Either way, the test
file is the same — only the import changes.

**Q3.** The brief mentions `assets/omo-meta-governor.schema.json`
should be regenerated as part of the release pipeline. Should
`scripts/release.ts` regenerate it before bumping `package.json`, or
trust that the dev has already done so? **Recommendation:** regenerate
as part of step 4b (`bun run build`), which already invokes
`writeSchemaFile()` per `build.ts:42-46`. No new step needed.

**Q4.** The PowerShell backtick issue from v0.37.2 was specifically
inside `gh release create --notes "..."`. The new script uses
`--notes-file` (file argument, not inline string), which is the right
fix. But should the script also support `--notes` (inline) for
backward compatibility? **Recommendation:** no — `--notes-file` is the
canonical path; `--notes` is a footgun.

**Q5.** The new `test-windows-flaky` workflow file triggers on
`pull_request` to `main`. Should it also trigger on
`pull_request` to other branches? **Recommendation:** no — branch
protection rules and PRs against `main` are the only ones that
matter for the merge gate. Branch-PRs get the main `ci.yml`
coverage.

**Q6.** The release script writes a temporary `.release-notes-v<X>.md`
file. Where should it live (cwd, `dist/`, `tmp/`) and when should it
be cleaned up? **Recommendation:** cwd, cleaned in the `finally` block
of step 7. If the script crashes between write and gh invocation, the
file is left behind — that's intentional (operator can inspect it).
The cleanup todo lives in §5's failure recovery matrix.
